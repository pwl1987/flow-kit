中间差点放弃好几次。有几套光配置就要一天，跑起来跟README说的完全不是一回事。还有几套你一看就知道不是给独立开发者准备的。

最后剩5套值得聊的。这篇不搞参数横评，只聊实际用的体感。

先点个关注吧！

## Everything Claude Code：全家桶

这套是Star数最高的，接近十五万。配置量也最恐怖——近50个agent、80多个command、180多个skill。全装上的话，Claude Code基本变成一个微型开发团队。前端、后端、数据库、测试、文档，每个岗位都配了专人。

我装完试了一周，然后卸掉了八成。

问题不在组件本身。问题是全堆在一起之后，启动慢得明显，上下文里各种skill定义互相抢资源。更要命的是——你每次干活前得先想清楚该调哪个agent、走哪条命令。思考成本比实际干活还高。

**适合谁** ：大团队里需要统一工具链的场景。或者你对定制有执念，愿意花大量时间打磨配置。152个subagent的配置都可以直接copy，省去从零搭建的时间。

**不适合谁** ：如果你连CLAUDE.md都没写到60行，先别碰这个。

**我的使用建议** ：不全装。挑5到8个跟你日常工作最相关的agent和skill。其他的留着，哪天需要了再按需加载。

## Superpowers：极简规则派

Star数跟全家桶差不多，也是十四万出头。但配置量少了不止一个数量级——只有5个agent、3个command、14个skill。

理念也完全不同。它走的是TDD-first路线，外加一套叫"Iron Laws"的硬约束——翻译过来就是：测试不写完，代码一行都不准动。

实际用下来最明显的感受：Superpowers跟Claude Code原生功能嵌得很紧，不像外挂，更像原生扩展。尤其是Plan阶段的增强——它会强制你检查这块需求在知识库里有没有支撑、上下文还剩多少、拆分粒度合不合理。

**适合谁** ：对质量和流程一致性要求高的项目。个人开发者也能用，学习曲线不陡。

**不适合谁** ：如果你的开发习惯是"先写代码再补测试"，Superpowers会让你很痛苦。它在执行阶段会反复提醒你写测试，对敏捷型开发不太友好。

**我的使用建议** ：核心流程（TDD-first的Plan → Execute → Review）保留，周边的验证规则可以按项目调整。别把所有Iron Laws都打开，选最关键的3到5条。

## Spec Kit：规格驱动派

八万七的Star。核心思路就一个：先写清楚你要什么，再让AI动手。

它的流程强制你先出一份详细的规格文档——需求描述、接口定义、数据模型、边界条件、验收标准，一样不能少。文档过关了，才进入代码生成阶段。

我拿一个分子对接的数据处理管线实测了一下。光规格就磨了一个小时——输入格式、输出字段、精度要求、异常情况处理，全得写清楚。但规格定稿之后，Claude一次就生成了能通过全部测试的代码——边界条件全覆盖，结构也干净。我后来对比了一下，同一个管线不写规格直接让Claude写，来回改了四版才定型。前面花的那一小时，后面全赚回来了。

**适合谁** ：大项目，多模块协作，对代码一致性要求高。或者你本身已经习惯先写设计文档再编码。

**不适合谁** ：小项目、原型验证、快速迭代场景。规格写一个小时，原生Claude Code十分钟就干完了。

**我的使用建议** ：大模块走Spec Kit流程，小功能不用走。找到你的规模分界线。我自己的分界线是"如果不需要跟PM对齐需求就不写规格"。

## gstack：角色扮演派

近七万Star。玩法跟前三套完全不同——它让Claude扮演不同角色：研究思路设计、算法选型、代码实现、测试验证。不是同时扮，是分阶段切换。官方给这套玩法起了个名字叫"role personas"加"parallel sprints"。

这个跟Agent Teams的区别在哪？Agent Teams是多个agent各干各的，并行推进。gstack是同一个agent在不同阶段换不同脑子，按顺序模拟一整个研究项目的工作流。

我跑了一遍完整流程，新鲜是挺新鲜的。但也明显感觉到一个问题：换角色本身也吃上下文。从研究设计切到算法选型再切到代码实现，每换一次都要重新加载角色设定和约束。三轮下来，上下文用掉不少。

**适合谁** ：一个人做全栈项目，需要完整的产品思维链。或者你想体验"一个人就是一个团队"的工作方式。

**不适合谁** ：如果你本身工作就是在团队里，不需要模拟角色协作。直接让Claude写代码就行。

**我的使用建议** ：不要每个任务都走完整角色链。只在需求模糊、需要从零设计的时候启动。就像你不会在改个变量名的时候开研究方案评审会。

## 原生轻量：什么工作流都不用

这是第五个选项。也是被低估得最厉害的选项。

仓库作者自己也在文档里写了：小任务用原生Claude Code就够了，比任何重型工作流都快。

我用下来的感受完全一致。上面四套都装过一遍之后，现在我90%的时间干脆什么工作流都不开。改个变量名、修个单行bug、写个工具函数——一句话扔过去，三分钟之内搞定。

复杂任务才上工作流。而且就算上工作流，也只在Plan和Review阶段使用，执行阶段还是回到原生模式。

## 选型速查

| 场景 | 推荐方案 |
| --- | --- |
| 小任务（5分钟以内） | 原生Claude Code |
| 个人项目，日常开发 | Superpowers 或 原生 |
| 多模块大项目 | Spec Kit + Superpowers |
| 个人全栈开发 | gstack（仅设计阶段） |
| 团队协作 | Everything Claude Code（按需组件） |
| 最不确定该选哪个 | Superpowers → 好用就留着，不好用换原生 |

## 选了之后呢

选工作流这件事，选错不算坑。选了之后不敢换，那才是真坑。

我用Superpowers用了两个月，觉得不错。后来试了Spec Kit，发现有些东西Spec Kit做得更好。现在我的实际工作流是：Plan阶段用Superpowers的Plan Mode扩展，执行阶段大部分用原生，大模块的规格用Spec Kit的方式写，偶尔在探索阶段开gstack的角色模式跑一遍完整逻辑链。

这不是标准的、干净的、可推广的工作流。但它是最适合我自己的。

Boris说过，就连他们自己团队里，每个人用Claude Code的方式都完全不一样。工作流就是个起点。好用的版本都是自己改出来的。
