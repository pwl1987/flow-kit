一天天的 *2026年4月13日 22:02*

事情是这样的。

我之前装了不少 Skills，涉及多个领域，比如分析需求、做技术方案设计、做 TDD、写 PPT 等等。按理说装上就该自动工作了对吧。

结果呢，几乎每次我都得手动跟 Claude 说，「帮我用 xxx skill 来做」。

你敢信？？？

这种感觉就像你给手机装了一堆自动化快捷指令，结果每次都得自己手动点开。那我装它干嘛。

我一直以为是自己的问题，可能指令不够明确，或者用的方式不对。直到最近看到一篇专门讲怎么写好 Skills 的指南，里面把这类问题归纳得特别清楚。它总共列了五种 Skill 容易出问题的模式，我挨个看完之后，有一种「原来如此」的感觉。

**第一种叫「沉默的 Skill」。**

就是你明明输入了应该触发它的请求，Claude 就像没看见一样，直接用通用方式回答了。原因是 Skill 的触发描述写得太弱。Claude 这玩意本来就比较保守，如果描述和你说的话对不上，它宁愿不触发。

举个例子，你的 Skill 描述写的是 spreadsheet processing，但你实际说的是「帮我 clean up 这个 CSV」。在人看来这明明是一回事，但 Claude 觉得对不上，就沉默了。

修法倒也简单，把用户可能说出来的各种表述都穷举进去。clean up、fix、CSV、data file，至少列 5 到 7 种触发语。越直白越好。

**第二种，反过来，叫「劫持型 Skill」。更烦人。**

你在做完全无关的事，某个 Skill 突然跳出来抢活。原因是触发范围写得太宽，又没有标明什么时候不该触发。

这个我是真的深有体会。我最开始图省事，装了一个叫 everything-claude-code 的大插件，名字就很霸气对吧，everything。结果它覆盖面实在太广了，我想调用别的 Skill 的时候，它经常先跳出来把活抢了。搞得我后来干脆卸掉了，从中提炼了几个我实际需要的。

修法也很直觉，给 Skill 补上负边界。把那些「看起来像但其实不是」的场景列出来，明确写上 Do NOT use for xxx。

**第三种叫「漂移型 Skill」** 。触发是对的，但产出跟你预期的不一样。原因是说明写得有歧义，Claude 每次理解的方式不同。解法是把所有模糊指令换成具体的、可测试的表述。「Handle appropriately」这种话没用，你得写成「如果输入缺少必需字段，先向用户追问，再继续执行」。

**第四种叫「脆弱型 Skill」** 。正常输入时表现不错，一碰到奇怪输入就崩。缺字段、格式错误、指令矛盾，随便一个就能让它翻车。解法是拿最糟糕的输入去喂它，每崩一次就补一条明确规则。

**第五种叫「过度发挥型 Skill」** 。输出里多出了你没要求的解释、额外章节或者自由发挥。你写了要做什么，但没写不要做什么，Claude 就开始加戏了。解法是补上明确的范围约束，「只输出指定格式，不要添加解释性文字」。

这五种问题，一二两种出现频率最高，也最让人困惑。三四五种相对好排查，因为至少 Skill 触发了，你能看到输出哪里不对。但沉默和劫持是最坑的，因为你可能根本没意识到是 Skill 的设计问题，一直以为是自己用的方式不对。

就像我之前那样。

说真的，就算你把触发描述写得再好，也很难做到 100% 准确。Claude 的判断毕竟有概率性。

然后我发现了一个特别暴力但有效的解法。

有个叫 superpowers 的工作流 [给 Claude Code 装上超能力：Superpowers 工作流为什么这么强](https://mp.weixin.qq.com/s?__biz=MzY4NTIyNzk2OA==&mid=2247483761&idx=1&sn=98da151c9ca817313d2675cdfc33e335&scene=21#wechat_redirect) ， **里面有一个叫 using-superpowers 的 Skill，干的事情很简单，就是确保一定会被触发** 。

怎么做到的呢。

它用了一个 SessionStart hook，在每次对话开始的时候就把自己强制注入进去。不是等 Claude 自己判断要不要触发，而是直接塞到上下文里，你没得选。

然后更有意思的来了。它列了一个「Red Flags」，把 Claude 所有可能用来逃避触发 Skill 的借口，全部堵死了。

Claude 心想「这只是个简单问题，不需要 Skill」，清单说，问题也是任务，检查 Skill。

Claude 心想「让我先看看代码再说」，清单说，Skill 会告诉你怎么看，先检查 Skill。

Claude 心想「我记得这个 Skill 的内容」，清单说，Skill 可能已经更新了，读当前版本。

Claude 心想「用 Skill 太大材小用了」，清单说，简单的事情会变复杂，用它。

Claude 心想「我先干完这一件事再说」，清单说，检查 Skill 在一切行动之前。

一共 12 种逃避借口，每一种都给了反驳。

我看到这个设计的时候愣了一下。

**它说到底不是在教 Claude 什么时候该触发 Skill，而是在堵死 Claude 所有「不触发」的退路。思路完全反过来了。**

默认不是「判断要不要用」，而是「只要有 1% 的可能性相关，就必须触发」。

这个 1% 的阈值特别关键。正常情况下 Claude 大概要 70% 以上的把握才会主动触发一个 Skill，但 using-superpowers 直接把阈值拉到了 1%。宁可误触发再判断不需要，也不能漏掉。

你想想看，这其实是两种完全不同的设计思路。

大多数人写 Skill，走的是「精确匹配」路线。把触发条件写准，让 Claude 自己判断。

superpowers 走的是「强制覆盖」路线。不信任 Claude 的判断，直接用机制兜底。

两种思路都对，但面对的问题不一样。

不过说到这个，我倒是想多聊一句。

现在社区注册表里已经有 9 万多个 Skills 了，很多人看到好的就装，装完发现不好用再换。 **我自己也经历过这个阶段，装了 everything-claude-code，又装了一堆零散的，最后发现它们之间互相打架，还不如不装。**

我自己的感受是，Skill 这东西不是装得越多越好。你得想清楚自己真正高频重复的任务是什么，然后针对性地装。同时还有一个容易忽略的点，Skill 分全局安装和项目级安装。全局的放在 ~/.claude/skills/ 下面，所有项目都会加载。项目级的放在项目根目录的.claude/skills/ 下面，只在那个项目里生效。

如果你把所有 Skill 都装成全局的，那每次对话 Claude 都要扫一遍所有 Skill 的触发描述，装多了就是互相干扰。像 code review 这种每个项目都需要的可以全局装，但像特定项目的写作风格、特定团队的代码规范这些，放在项目级就好了。

**坦率的讲，少而精，比多而杂靠谱得多** 。

其实这个道理放到任何工具设计上都一样。一个工具如果每次都需要你手动告诉它该上场了，那跟没装也没啥区别。但反过来，如果你装了太多工具它们互相抢着上场，那也是另一种混乱。

找到那个平衡点，才是真的好用。

所以如果你也在用 Skills，也踩过类似的坑，可以去看看这两个东西。 **一个是那篇写 Skills 的完整指南，教你怎么从根上把触发描述写对，五种失败模式和修法都讲得很清楚。一个是 superpowers 这个项目，直接用机制解决触发问题。**
