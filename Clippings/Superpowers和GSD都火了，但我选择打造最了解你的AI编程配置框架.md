## 引子：一个普通开发者的真实困境

最近AI编程圈很热闹。

Superpowers发布不到两个月GitHub狂飙100K星，GET SHIT DONE（GSD）15K星被Amazon、Google的工程师实战使用。它们都在解决同一个问题—— **AI写代码快是快，但不靠谱** 。

Superpowers的方案是给AI装一套"技能系统"，自动触发TDD、代码审查、系统调试。GSD的方案是搞一个"指挥系统"，用多智能体编排+上下文工程，把大任务拆成小任务给不同的AI做。

两个方案都很棒。但我用了一段时间后，发现一个尴尬的事实——

**它们解决的是"AI怎么工作"的问题，但没解决"AI怎么理解我的项目"的问题。**

什么意思？

你让AI遵循TDD流程，很好。但它知道你这个项目的数据库用的是SQLite还是PostgreSQL吗？知道你的API命名风格是RESTful还是GraphQL吗？知道你上周刚把ORM从SQLAlchemy换成了Tortoise吗？知道你之前踩过一个"异步session在测试中必须用独立fixture"的坑吗？

**不知道。每次打开新对话，AI都像第一天入职的员工——一切从零开始。**

你得重新告诉它项目背景、技术选型、编码规范、架构决策……这些"上下文"并不是一两句话能说清的。而一旦说不清，AI就开始"猜"——猜错了，代码就偏了，你又得花时间纠正。

我做了一个真实的生产项目，15个功能模块，563个测试用例。在这个过程中，我被这个问题反复折磨，最终逼出了一套自己的解决方案。

不是框架，不是工具，不需要安装任何东西—— **就是一套配置文件，复制到你的项目里，AI立刻"变聪明"。**

我把它开源了，叫 **AI Coding OK** 。

## 一、先说痛点：AI编程的"三大失忆症"

在写AI Coding OK之前，我遇到的问题可以归结为三种"失忆"：

## 失忆症一：跨会话失忆

你上午跟AI说："咱们这个项目用FastAPI + SQLite + Jinja2模板，路由层不写业务逻辑，业务逻辑全放service层。"AI说好的。你们愉快地写了一上午代码。

下午你开了一个新对话，说："帮我加一个用户管理模块。"

AI：好的！我来用Flask给你写一个……

**它全忘了。**

你说，我把之前的对话截图给它看不就行了？不行。第一，截图太多了记不住。第二，AI的上下文窗口就那么大，你把历史对话全塞进去，等于占用了写代码的"脑容量"。

## 失忆症二：规范失忆

你在第一次对话里跟AI说："函数命名用snake\_case，类名用PascalCase，所有函数都要有类型注解和docstring。"AI遵守得很好。

换个对话，它又开始写getUserName（驼峰命名）了，docstring也不写了，类型注解更是想起来才加。

你反复纠正，反复提醒。AI反复道歉，反复犯错。

**不是AI不听话，是它根本没有"长期记忆"。每次对话都是一张白纸。**

## 失忆症三：决策失忆

这是最坑的一种。

你上周和AI讨论了半天，决定"用SQLite的WAL模式来提升并发读性能，不做复杂并发写"。这是一个重要的架构决策，影响后续所有数据库相关的代码。

但这个决策记在哪？记在上周那个已经关掉的对话里。

本周AI开始写新功能时，它不知道这个决策，于是写了一段"用悲观锁处理并发写入"的代码——直接和你的架构矛盾了。

你发现问题的时候，代码已经写了一大堆。推倒重来？心疼。勉强缝合？埋雷。

**这些"失忆症"的根源只有一个：AI没有持久化的项目知识库。**

## 二、AI Coding OK是什么？三句话说清楚

**第一句：它是一套配置文件模板。** 你把它复制到你的项目里，GitHub Copilot就会自动读取、自动遵循。

**第二句：它给AI装了一个"记忆系统"和一本"操作手册"。** AI不再是每次从零开始的实习生，而是一个了解你的项目、记得住决策、遵守你的规范的"驻场工程师"。

**第三句：它从一个563个测试用例的真实生产项目中沉淀而来。** 不是纸上谈兵，是真刀真枪的实战经验。

用一个比喻——

> 如果说Superpowers是给AI加了一套"技能buff"，GSD是给AI派了一个"项目经理"，那AI Coding OK就是给AI发了一本你的项目的员工手册——里面有公司文化、岗位职责、操作规程、历史教训、通讯录……新员工入职第一天读完这本手册，就能快速上手，不犯低级错误。

**技能和管理是通用的，但员工手册是你自己的。**

## 三、核心设计：三层配置 + 三级记忆 + PDCA工作流

AI Coding OK的架构很简洁，但每一层都有明确的用途。

## 三层配置体系

| **层级** | **文件** | **作用** | **类比** |
| --- | --- | --- | --- |
| 第一层 | AGENTS.md | 项目地图，AI最先读取 | ️ 作战地图 |
| 第二层 | copilot-instructions.md | 全局行为指令 | 岗位说明书 |
| 第三层 | agent/ 子目录 | 编码规范、工作流、记忆 | 操作手册 |

**AI读取的顺序是：先看地图（知道项目全貌）→ 再看说明书（知道自己该怎么做）→ 最后翻手册（知道具体怎么操作）。**

这三层的设计思路是： **信息从粗到细、从全局到局部、从稳定到易变。** AGENTS.md可能几个月都不改，task-history.md每次任务都要更新。分层之后，AI可以按需加载，不用每次都读全部内容——这也是一种"上下文工程"。

## 三级记忆系统——这才是真正的杀手锏

| **记忆类型** | **文件** | **存什么** | **更新频率** |
| --- | --- | --- | --- |
| 长期记忆 | project-memory.md | 架构、约束、已知坑 | 很少变化 |
| 中期记忆 | decisions-log.md | 技术决策（ADR格式） | 架构变更时 |
| 短期记忆 | task-history.md | 近30条任务摘要 | 每次任务后 |

这套记忆系统解决的就是前面说的"三大失忆症"：

- **跨会话失忆？**
	→ AI每次开始任务，先读project-memory.md，项目的技术栈、核心模块、关键约束一目了然。
- **决策失忆？**
	→ 所有重要的技术决策都记录在decisions-log.md里，用标准的ADR（Architecture Decision Records）格式，包含背景、方案对比、选择理由、影响范围。AI读完就知道"为什么选了这个方案"，不会做出矛盾的决策。
- **规范失忆？**
	→ coding-standards.md里白纸黑字写着命名规范、代码风格、测试要求。AI每次写代码都会参考。

**最妙的是：记忆的更新也是AI自己做的。**

每次任务完成后，PDCA工作流的最后一步"Act"会要求AI：更新task-history.md记录本次任务、如果有架构变更就更新decisions-log.md、如果有项目事实变化就更新project-memory.md。

**AI给自己写笔记，下次自己看。** 形成了一个自我强化的闭环。

## PDCA工作流：让AI做事有章法

```
Plan（读记忆 → 理解需求 → 出实施计划）
  → Do（写代码 + 写测试）
    → Check（跑测试 → 验回归）
      → Act（更新记忆）
```

这是经典的质量管理循环，用在AI编程上刚好——

- **Plan阶段不准直接动手写代码。**
	必须先读记忆文件获取上下文，理解任务的真实意图，输出实施计划（思路、步骤、影响范围），确认后才能开始。
- **Do阶段写功能必须带测试。**
	不是写完功能"回头补测试"，而是写一个功能、跟一个测试，确保每段代码都有验证。修Bug更严格——必须先写一个失败的测试用例来复现Bug，然后再修。
- **Check阶段不是"看起来能跑"就完事。**
	要跑全部相关测试，确认没有回归（改了A不能把B搞坏）。
- **Act阶段沉淀经验。**
	把这次做了什么、踩了什么坑、做了什么决策记录下来，留给下一次用。

**Plan → Do → Check → Act → Plan → Do → Check → Act……** 每一轮循环都让项目的"知识库"更丰富，AI的上下文更准确，代码质量更高。

## 四、多角色切换：一个AI顶六个岗位

AI Coding OK定义了六种角色，AI根据当前任务自动切换：

| **角色** | **做什么** | **什么时候启动** |
| --- | --- | --- |
| 产品经理 | 分析需求、写用户故事、定验收标准 | 需求模糊时 |
| ️ 架构师 | 设计方案、评估技术选型、记录决策 | 新功能设计时 |
| 后端工程师 | 写业务逻辑、API、数据模型 | 编码实现时 |
| 前端工程师 | 写页面、交互逻辑 | 涉及UI时 |
| 测试工程师 | 写单元测试、集成测试、边界测试 | 验证阶段 |
| Code Reviewer | 审查代码质量、安全性、规范符合度 | 提交前 |

**不是你手动切换，而是AI根据任务上下文自动判断用哪个角色。**

你说"分析一下这个需求"——产品经理模式启动，输出用户故事和验收标准。 你说"实现这个功能"——先切到架构师模式出设计方案，确认后切到工程师模式写代码，写完切到测试工程师模式补测试，最后切到Reviewer模式自检。

**一个AI，六个角色，完整覆盖软件开发的全生命周期。**

## 五、三级行为权限：有些事AI可以自己做，有些事必须问你

这是一个很多AI编程方案忽略的问题—— **AI的行为边界在哪里？**

写代码的时候，有些操作是安全的、可逆的，AI可以自主判断。有些操作是高风险的，必须经过人类确认。还有些操作是绝对禁区，AI碰都不能碰。

AI Coding OK定义了三级权限：

| **级别** | **含义** | **示例** |
| --- | --- | --- |
| 可自主执行 | 安全操作，做了不会出事 | 优化命名、补测试、修明显Bug、加docstring |
| 需确认执行 | 有影响，但可讨论 | 新增依赖包、改数据库schema、改核心业务逻辑 |
| 禁止执行 | 碰了就可能出大事 | 删数据库、改密钥、改线上配置、发版本 |

**有了这三条线，你就可以放心让AI自主工作了。** 绿灯区的事它自己搞定，黄灯区的事它会先问你，红灯区的事它碰都不碰。

这就像给AI装了一个"安全围栏"—— **在围栏里，它可以自由发挥；围栏外，它自动停下。**

这可能是AI Coding OK最大的优势—— **极低的使用门槛** 。

```

cp-r ai-coding-ok/.github your-project/.github
cpai-coding-ok/AGENTS.md.template your-project/AGENTS.md
```

## Step 2：让AI帮你定制

打开Copilot Chat，说：

> 请阅读.github/下所有配置文件和AGENTS.md，这些文件中有{{占位符}}需要替换。我想做的东西是：一个给自己用的记账小工具。请自动替换所有占位符。

**你不需要懂什么是ORM、什么是WAL模式、什么是ADR格式。** 你只需要用你自己的话说清楚你想做什么，AI会自动推断合适的技术选型、架构方案和编码规范，然后一次性填好所有配置。

## Step 3：开始开发

从现在起，你的AI会：

- ✅ 每次开始任务先读记忆，理解上下文
- ✅ 先出计划，确认后再写代码
- ✅ 写功能必带测试
- ✅ 完成后自动更新记忆

**没有需要安装的包，没有需要学习的命令，没有需要配置的环境。** 复制文件、让AI填好、开始干活——三步搞定。

## 八、它跟Superpowers、GSD有什么不同？

这三个项目解决的都是"AI编程不靠谱"的问题，但切入角度完全不同：

| **项目** | **核心思路** | **一句话定位** | **适用场景** |
| --- | --- | --- | --- |
| **Superpowers** | 技能注入——给AI加TDD、代码审查等工程习惯 | AI的"技术总监" | 需要严格工程纪律的团队 |
| **GSD** | 多智能体编排——把大任务拆成小任务，隔离上下文 | AI的"项目经理" | 中大型项目的全流程管理 |
| **AI Coding OK** | 配置驱动——用结构化文档给AI注入项目知识和行为规范 | AI的"员工手册" | 任何需要AI长期参与的项目 |

**Superpowers管的是"工程纪律"——怎么写代码、怎么测试、怎么调试。**

**GSD管的是"任务调度"——做什么、什么顺序做、怎么验收。**

**AI Coding OK管的是"项目知识"——这个项目是什么、有什么约束、做过什么决策、踩过什么坑。**

它们不是竞争关系，而是 **互补关系** 。你完全可以同时使用：用GSD管理大的工作流，用Superpowers保证工程纪律，用AI Coding OK给AI注入项目上下文。三层加在一起，AI编程的可靠性会有质的飞跃。

但如果你只想用一个—— **AI Coding OK的上手成本最低** 。不需要安装任何东西，复制文件就能用。

## 九、为什么我选择自己做，而不是只用现成的？

说实话，Superpowers和GSD都是非常优秀的项目，我也在用。

但在实际项目中，我发现有一类问题它们覆盖不到—— **项目级的个性化知识管理** 。

举个真实的例子。我的项目里有一个"轮询调度"的功能，需要跳过非活跃的条目。这个逻辑很简单，但有一个坑：在特定的边界情况下（所有条目都非活跃），会进入死循环。

我第一次踩了这个坑，花了两小时定位。修好之后，我把这个坑记录在了project-memory.md的"已知问题&常见坑"里。

后来AI又遇到了类似的场景——它读了记忆文件， **主动避开了这个坑** ，还在代码里加了防御性检查。

**这种"项目特有的经验传承"，是通用型工具做不到的。** Superpowers可以教AI"怎么写好代码"，但教不了AI"你这个项目的轮询功能有个死循环的坑"。GSD可以帮AI"拆解任务"，但拆不出"上次做类似功能时踩过什么坑"。

**AI Coding OK做的事情，本质上是把"你的项目经验"结构化、持久化，让AI可以读取和利用。**

这也是为什么我说它是"为自己量身定做"的—— **每个人的项目不同，踩的坑不同，积累的经验不同。AI Coding OK提供的是框架和模板，具体内容是你自己的项目填进去的。**

## 十、一个可能被忽视的亮点：Memory Check CI

AI Coding OK里有一个小巧但很实用的CI工作流——memory-check.yml。

它的作用是： **当你提交的PR修改了核心代码，但没有更新记忆文件时，自动在PR里留一条评论提醒你。**

```
记忆更新提醒

本次PR包含核心代码变更，但未更新项目记忆文件。

请检查是否需要更新：
-project-memory.md — 项目事实变更
-decisions-log.md — 新的技术决策
-task-history.md — 任务记录
```

为什么这个很重要？

因为 **记忆系统的价值取决于它是否被及时更新** 。如果你做了一个重要的架构变更，但忘了更新记忆文件，下次AI读到的就是过时的信息——比不读还危险。

这个CI工作流就像一个尽职的"记忆管理员"—— **你可以忘，但它不会忘提醒你** 。

## 十一、它的局限性：实话实说

任何工具都有边界，AI Coding OK也不例外：

**1\. 目前主要适配GitHub Copilot生态。** 配置文件的目录结构（.github/）和文件命名（copilot-instructions.md）是按照Copilot的约定设计的。如果你用的是Claude Code或Cursor，需要做一些适配（把配置内容迁移到对应平台的指令文件中）。

**2\. 记忆需要人工维护的纪律。** 虽然PDCA流程会让AI自动更新记忆，但AI更新的质量取决于你对AI的约束力度。如果你每次都跳过"Act"阶段，记忆文件就会逐渐过时。

**3\. 它是配置框架，不是自动化工具。** GSD有命令行、有自动调度；Superpowers有自动触发的技能。AI Coding OK提供的是"规范和知识"，而不是"自动化流程"。AI的行为改善来自它"读懂了你的配置"，而不是某个程序在背后调度。

**4\. 模板需要定制。** 开箱即用的是模板（带{{占位符}}），你需要根据自己的项目填充具体内容。虽然Step 2可以让AI帮你填，但最终的Review还是需要你自己做。
