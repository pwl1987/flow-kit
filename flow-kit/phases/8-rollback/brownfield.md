# Phase 8: 变更回滚 — 棕地项目

> 适用：已有代码库的业务迭代开发
> 棕地项目回滚需特别关注向后兼容性和数据迁移

## 棕地项目回滚重点

- 确保回滚后系统仍可正常运行
- 保持向后兼容性
- 数据迁移需要回滚脚本支持

## 执行步骤

### Step 0: 三档分级判定

收到回滚请求后，先判定严重等级：

| 等级 | 条件 | 动作 |
|------|------|------|
| P0 | 生产故障/数据丢失 | **先回滚，再诊断**，完成后做事后 5 件事 |
| P1 | 功能异常但可绕过 | 三问澄清 → 快速修复 → 事后 5 件事 |
| P2 | 体验问题/非阻塞 | 走正常修复流程 |

### P1 三问澄清

1. 影响哪些用户/功能？
2. 有无临时绕过方案？
3. 修复需要多久？

### Step 1: 评估影响

1. **问题定位**
   - 哪些功能受影响
   - 影响范围
   - 回滚必要性

2. **决策**
   - 回滚 vs 热修复
   - 全量回滚 vs 增量回滚

### Step 2: 执行回滚

1. **代码回滚**

   ```bash
   git revert <commit-sha>
   git push
   ```

2. **数据库回滚**

   ```bash
   npm run db:migrate:rollback
   ```

3. **配置回滚**
   ```bash
   git checkout HEAD~1 .env
   ```

### Step 3: 验证

1. **功能验证**
   - 核心功能正常
   - 受影响功能恢复

2. **监控**
   - 错误率下降
   - 性能正常

### Step 4: RCA 事故报告

完成回滚后，填写事故报告：

```markdown
## 事故报告

### 基本信息
- 时间：
- 影响范围：
- 分级：P0/P1/P2

### 根因分析（5 Whys）
1. 为什么发生？
2. 为什么没在测试阶段发现？
3. 为什么监控没有提前告警？
4. 为什么回滚是必要的？
5. 为什么流程没能阻止？

### 修复方案
- 短期：
- 长期：

### 事后 5 件事
- [ ] 1. 根因分析（RCA）
- [ ] 2. 修复方案文档
- [ ] 3. 测试补充（防止复发）
- [ ] 4. 监控告警规则更新
- [ ] 5. 文档更新
```

## 输出物

- 事故报告
- 回滚记录
- 修复计划
