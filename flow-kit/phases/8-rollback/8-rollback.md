# Phase 8: Rollback - 变更回滚

## 触发条件
{{TRIGGER}}

### 手动触发
- 用户执行 `/flow-kit:rollback <target>`
- 用户通过 `flow-kit rollback` CLI 命令触发
- 触发前自动检查是否存在已标记的稳定点

### 自动触发
- 下游阶段验证失败且满足自动回滚条件
- Phase executor 检测到预设的回滚触发规则被激活
- 条件包括：连续 N 次验证失败、关键指标超过阈值

### 监控触发
- 外部监控系统检测到异常指标
- 健康检查端点返回错误状态
- 自定义监控规则触发（CPU、内存、错误率等）

## 核心行为
{{CORE_BEHAVIOR}}

### 回滚执行流程

1. **回滚评估**：评估问题的严重性和影响范围
2. **回滚策略选择**：
   - 完整回滚：恢复到上一稳定版本（commit + 生成文件）
   - 部分回滚：仅回滚问题功能
   - 热修复：在线修复而不回滚代码
3. **回滚执行**：执行选定的回滚策略
4. **验证确认**：确认回滚后的系统状态
5. **问题定位**：分析导致回滚的根本原因
6. **后续处理**：决定是重新修复还是废弃变更

### 安全护栏机制

- **确认提示**：回滚操作前显示影响范围预览，等待用户确认
- **备份创建**：自动创建当前状态快照，支持回滚到回滚前
- **影响范围预览**：列出受影响文件、变更点和依赖关系

### 强制回滚

- `--force` 参数跳过护栏确认提示
- 仅在紧急情况下使用，需事后记录原因
- 自动生成强制回滚日志供审计

## 边界情况
{{BOUNDARY_CASES}}

### 数据一致性
- 回滚时确保数据不丢失或损坏
- 执行数据完整性检查
- 必要时触发数据修复流程

### 级联回滚
- 多个相关变更都需要回滚时，按依赖关系排序
- 显示级联影响树，让用户确认所有受影响变更
- 支持批量回滚操作

### 无法回滚
- 系统状态不支持回滚时（如稳定点不存在）
- 提供诊断信息和替代方案
- 标记该变更状态为 `rollback-unavailable`

### 部分回滚失败
- 回滚操作部分成功时的处理
- 自动回退成功的部分，恢复原始状态
- 生成详细的部分回滚报告
- 保留手动干预的选项

### 回滚风暴
- 多个变更同时需要回滚的优先级处理
- 按严重程度和时间戳排序
- 提供批量处理选项，避免排队阻塞

## 输出物
{{OUTPUTS}}

### 回滚报告
- 回滚操作记录和结果
- 包含执行时间、影响范围、操作者信息

### 问题分析
- 导致回滚的问题根因
- 生成 `LESSONS.md` 条目供后续参考

### 恢复确认
- 系统恢复正常状态的确认
- 关键指标回归正常范围的验证

### 后续行动计划
- 是重新修复还是废弃变更
- 建议的修复步骤和责任人

### 流程状态更新
- 变更状态标记为 `Rolled-back`
- 更新 STATE.md 中的变更历史

## 用户调整标记
{{USER_ADJUST}}

### --adjust=promote
将某稳定点升级为更高优先级的回滚目标。

```
/flow-kit:rollback --target=phase-5 --adjust=promote
```

- 用于修复后重新标记为稳定
- 自动更新稳定点优先级
- 生成提升日志

### --adjust=demote
将某稳定点降级（谨慎操作）。

```
/flow-kit:rollback --target=phase-5 --adjust=demote
```

- 用于标记不稳定或存在风险
- 降低其在回滚候选中的优先级
- 记录降级原因

### --adjust=remove
移除稳定点标记（危险操作）。

```
/flow-kit:rollback --target=phase-5 --adjust=remove
```

- 不可逆操作，需二次确认
- 从回滚候选中彻底移除
- 保留审计追踪
