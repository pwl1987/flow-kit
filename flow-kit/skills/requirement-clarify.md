# Skill: Requirement Clarification (SKILL-30)

## WHEN_TO_USE

- **Phase**: Phase 1 — Requirement Gathering
- **Trigger**: 用户提出模糊、不完整或存在歧义的需求时
- **场景**:
  - 用户说 "做用户认证" 而非具体用例
  - 需求包含未定义的术语（如 "安全地处理"）
  - 缺少验收标准或成功定义
  - 发现多个利益相关者对需求理解不一致

## HOW_TO_USE

使用 **GRILL-ME** 问题模板进行系统化澄清：

### GRILL-ME 模板（5Ws + Edge Cases + Acceptance）

| 维度 | 问题 | 目的 |
|------|------|------|
| **G**oal | 这个功能的最终目标是什么？ | 理解真实需求 |
| **R**ole | 谁会使用这个功能？他们的背景？ | 确定用户画像 |
| **I**nput | 触发条件的输入是什么？ | 明确数据边界 |
| **L**imitation | 有什么技术或业务限制？ | 约束条件 |
| **L**ogic | 核心业务逻辑是什么？ | 处理规则 |
| **M**etric | 如何判断成功？验收标准？ | 可验证性 |
| **E**dge | 边界条件和异常情况？ | 完整性 |

### 执行步骤

1. **识别歧义**：扫描需求中的名词、动词是否明确
2. **应用模板**：对每个歧义点提出 GRILL-ME 问题
3. **记录澄清**：将回答追加到需求文档
4. **确认一致**：向用户确认澄清后的需求理解

## EXAMPLE

**原始需求**：
> "系统需要安全地处理用户数据"

**澄清过程**：
```
Q: Goal - "安全地"具体指什么？
A: 防止未授权访问、加密存储、审计日志

Q: Role - 哪些用户角色？
A: 普通用户（上传）、管理员（查看）、审计员（报告）

Q: Input - 用户数据的格式和来源？
A: JSON/表单提交，最大10MB，支持图片和文档

Q: Metric - 如何判断"安全"？
A: 通过安全扫描，OWASP Top 10 无漏洞，加密标准 AES-256

Q: Edge - 异常情况？
A: 加密失败怎么办？密钥轮换如何处理？
```

**澄清后需求**：
> "普通用户上传的文件使用 AES-256 加密存储，管理员可查看但需要双因素认证，审计日志保留 3 年，异常时记录错误并通知安全团队"

## NOTES

### 常见陷阱

| 陷阱 | 描述 | 解决方法 |
|------|------|----------|
| **歧义名词** | "用户"、"系统"、"数据" 指代不明 | 要求明确具体对象 |
| **未定义成功** | 没有验收标准 | 应用 SMART 原则 |
| **隐含假设** | 跳过看似 obvious 的细节 | 检查所有假设 |
| **范围蔓延** | 需求越做越大 | 明确 MVP 边界 |
| **技术绑定过早** | 解决方案限制需求 | 先理解问题，再讨论方案 |

### 验证检查

- [ ] 所有名词有唯一指代
- [ ] 每个动词可执行且可测试
- [ ] 验收标准包含量化指标
- [ ] 边界情况明确列出
- [ ] 用户确认理解一致

## D-22 增强：多需求排序与验收标准自动生成

### MoSCoW 优先级框架（可选扩展）

| 优先级 | 定义 | 交付要求 |
|--------|------|----------|
| **Must** | 核心功能，不实现则系统不可用 | 必须交付 |
| **Should** | 重要功能，但有替代方案 | 尽量交付 |
| **Could** | 增强功能，不影响业务 | 视资源情况 |
| **Won't** | 本次不实现 | 明确排除 |

**执行**：
1. 用户提供需求列表
2. 引导用户为每个需求标注 MoSCoW 优先级
3. 按 Must → Should → Could → Won't 排序
4. 输出需求优先级列表

### Kano 模型（可选扩展）

| 类型 | 特征 | 用户满意度 |
|------|------|------------|
| Must-be | 必须有，否则不满 | 线性正相关 |
| Attractive | 惊喜功能，超出预期 | 非线性正相关 |
| One-dimensional | 有则满意，无则不满 | 线性相关 |
| Indifferent | 无关紧要 | 无相关 |
| Reverse | 反向特征 | 有则不满 |

### 验收标准自动生成

**输入**：澄清后的需求描述

**输出**：
```markdown
## 验收标准 (Auto-generated)

### AC-1: [需求项名称]
- **Given** [前置条件]
- **When** [操作]
- **Then** [预期结果]

### AC-2: [需求项名称]
- **Given** ...
- **When** ...
- **Then** ...

### Edge Cases
- [边界条件 1]
- [边界条件 2]
```

**对接**：
- 生成的验收标准 → 传递给 task-master.md
- 生成的验收标准 → 传递给 verification.md

## 注意事项
- MoSCoW 和 Kano 作为可选扩展，不强制使用
- 验收标准自动生成对接下游 skills（task-master + verification）
