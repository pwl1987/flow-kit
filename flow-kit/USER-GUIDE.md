## 第一章：概述

### 1.1 什么是 flow-kit

flow-kit 是面向 Claude Code 的结构化开发流程工具包，提供完整的 8 阶段开发工作流、棕地护栏规则、可复用技能包、工程模板和参考材料。它旨在帮助开发团队在 AI 辅助编程环境中保持工程规范、控制上下文窗口使用率、并确保代码质量。

### 1.2 核心特性

| 特性               | 描述                                             |
| ------------------ | ------------------------------------------------ |
| **8 阶段工作流**   | 从需求立项到集成归档的完整开发流程               |
| **棕地护栏 B1-B6** | 六大护栏保护现有代码库免受破坏性变更             |
| **多代理编排**     | 支持并行执行多个子代理，主上下文维持在 30-40%    |
| **元技能包**       | 15+ 个可复用技能模块覆盖需求、开发、测试、审查   |
| **多语言支持**     | TypeScript、Python、Java、Go、Rust、PHP 工程规范 |
| **上下文预算**     | 智能 token 估算与预算管理，防止上下文溢出        |
| **Hooks 系统**     | 5 个自动化钩子实现质量门禁和通知                 |

### 1.3 适用场景

| 场景                     | 推荐配置                               |
| ------------------------ | -------------------------------------- |
| 简单功能变更（1-3 文件） | L0 极简模式，跳过 Phase 2-3            |
| 中等复杂度新功能         | L1 标准 8 阶段流程                     |
| 复杂架构变更             | L2-L3 完整流程 + 设计评审 + 多代理并行 |
| 棕地项目迭代             | 启用 B1-B6 全部护栏                    |
| 团队并行开发             | 多代理编排 + 角色分工                  |

### 1.4 术语表

| 术语               | 定义                                     |
| ------------------ | ---------------------------------------- |
| **Phase**          | 开发流程的一个阶段，共 0-8 九个阶段      |
| **Guardrail**      | 护栏规则，防止破坏性变更的安全检查       |
| **Skill**          | 可复用的技能模块，提供特定能力           |
| **Hook**           | 自动化钩子，在特定事件触发时执行         |
| **Context Budget** | 上下文窗口预算，控制 token 使用量        |
| **Subagent**       | 子代理，在独立上下文中执行任务的 AI 实例 |
| **Brownfield**     | 棕地项目，已有代码库的迭代开发           |
| **Greenfield**     | 绿地项目，从零开始的新项目开发           |

## 第二章：安装与配置

### 2.1 安装方式详解

flow-kit 提供四种安装方式，从"完整功能"到"轻量使用"依次介绍。

---

#### 方式一：克隆到项目（推荐深度用户）

```bash
# 进入你的项目目录
cd /path/to/your-project

# 克隆 flow-kit 作为 .flow-kit 目录
git clone https://github.com/pwl1987/flow-kit.git .flow-kit
```

**优点**：完整功能，自动更新，斜杠命令注册
**缺点**：污染项目仓库（.flow-kit 目录）

---

#### 方式二：复制核心文件（适合轻量使用）

```bash
# 复制核心文件到项目根目录
cp flow-kit/GO.md /path/to/project/
cp -r flow-kit/phases /path/to/project/
cp -r flow-kit/templates /path/to/project/
cp -r flow-kit/config /path/to/project/
```

**优点**：不污染仓库，轻量
**缺点**：需手动更新，无法使用自动命令注册

---

#### 方式三：作为 Git 子模块（适合团队共享）

```bash
# 添加为 git 子模块
git submodule add https://github.com/pwl1987/flow-kit.git .flow-kit
```

**优点**：版本可控，团队共享
**缺点**：需团队协作，子模块更新需单独操作

---

#### 方式四：符号链接（适合 flow-kit 开发者）

```bash
# 创建符号链接
ln -s /path/to/flow-kit .flow-kit
```

**优点**：可编辑源码，实时生效
**缺点**：路径强依赖，不适合移动项目

---

### 安装方式对比

| 方式             | 命令                      | 适用场景      | 完整功能 | 自动更新 | 团队友好 |
| ---------------- | ------------------------- | ------------- | :------: | :------: | :------: |
| 方式一：克隆     | `git clone ... .flow-kit` | 深度使用      |    ✅    |    ✅    |    ❌    |
| 方式二：复制     | `cp flow-kit/GO.md ...`   | 轻量使用      |    ❌    |    ❌    |    ❌    |
| 方式三：子模块   | `git submodule add ...`   | 团队共享      |    ✅    |    ❌    |    ✅    |
| 方式四：符号链接 | `ln -s ... .flow-kit`     | 开发 flow-kit |    ✅    |    ✅    |    ❌    |

---

### 2.2 详细安装步骤（方式一：克隆）

无论你是新手还是有经验的开发者，按照以下步骤即可完成安装。

#### Step 1: 检查环境

```bash
# 验证 Git 已安装
$ git --version
git version 2.39.0

# 验证 Claude Code 已登录
$ claude --version
Claude Code v1.0.0

# 验证 Bash 版本（需要 4.0+）
$ bash --version
GNU bash 5.1.16

# 验证 jq 已安装（用于 JSON 处理）
$ jq --version
jq-1.6
```

**如果 jq 未安装**：

```bash
# macOS
brew install jq

# Ubuntu/Debian
sudo apt-get install jq

# Alpine
apk add jq
```

#### Step 2: 克隆 flow-kit 到项目

```bash
# 进入你的项目目录
$ cd /path/to/your-project

# 克隆 flow-kit
$ git clone https://github.com/pwl1987/flow-kit.git .flow-kit
Cloning into '.flow-kit'...
remote: Enumerating objects: 527, done.
remote: Counting objects: 100% (527/527), done.
remote: Compressing objects: 100% (302/302), done.
remote: Total 527 (delta 212), reused 487 (delta 180)
Receiving objects: 100% (527/527), 675.01 KiB | 2.30 MiB/s, done.
Resolving deltas: 100% (212/212), done.
```

#### Step 3: 初始化目录结构

```bash
# 创建必要的目录
$ mkdir -p .planning              # 规划目录：存放项目上下文
$ mkdir -p .specs                  # 变更规格目录：存放每次变更的详细规格
$ mkdir -p .claude/commands       # 斜杠命令目录（Claude Code 专用）

# 查看目录结构
$ tree -a -L 1
.
├── .flow-kit/            # flow-kit 核心文件
├── .planning/            # 你的项目规划
├── .specs/               # 变更规格

```

**目录作用说明**：

| 目录                | 作用                                            | 新手是否需要操作 |
| ------------------- | ----------------------------------------------- | :--------------: |
| `.flow-kit/`        | flow-kit 核心文件，不要修改                     |     ❌ 禁止      |
| `.planning/`        | 存放项目上下文文件（PROJECT.md, ROADMAP.md 等） |     ✅ 需要      |
| `.specs/`           | 存放每次变更的详细规格（每个变更一个子目录）    |     ✅ 需要      |
| `.claude/commands/` | Claude Code 斜杠命令注册目录                    |     ❌ 自动      |

#### Step 4: 注册斜杠命令

**方式一：首次 Claude Code 会话自动注册（推荐）**

当你首次在项目目录中启动 Claude Code 会话时：

1. Claude Code 会自动执行 session-start hook
2. hook 运行 `generate-commands.sh --force` 脚本
3. 所有斜杠命令自动注册到 `.claude/commands/` 目录
4. 重启 Claude Code 会话后，命令即可使用

**方式二：手动触发注册（通过 shell）**

如果你想立即注册命令而不重启 Claude Code：

```bash
# 在项目目录中运行
$ cd /path/to/your-project
$ ./.flow-kit/scripts/generate-commands.sh --force

==========================================
flow-kit 斜杠命令生成器 v1.13
==========================================
源目录: /path/to/your-project/.flow-kit/commands
输出目录: /path/to/your-project/.claude/commands
模式: live (force)
==========================================

--- dev 开发流程命令 ---
[生成] flow-kit:dev-minimal -> /path/to/your-project/.claude/commands/flow-kit:dev-minimal.md
[生成] flow-kit:dev-health -> /path/to/your-project/.claude/commands/flow-kit:dev-health.md
...

==========================================
完成: 59 生成, 0 跳过 (共 59 个命令)
==========================================
```

**方式三：注册 hooks 后自动生效**

```bash
# 安装 hooks（可选，推荐）
$ ./.flow-kit/flow-kit.sh hooks install

# hooks 安装后，每次 Claude Code 启动都会自动注册命令
$ /flow-kit:health

[flow-kit] hooks 已就绪（5/5）
[flow-kit] 斜杠命令已就绪（59 个命令）
✅ 健康检查通过
```

**注册命令的工作原理**：

```
┌──────────────────────────────────────────────────────────────────┐
│                     斜杠命令注册流程                              │
├──────────────────────────────────────────────────────────────────┤
│                                                                   │
│  方式一：session-start hook（自动）                               │
│  ┌─────────────────┐                                             │
│  │ Claude Code 启动 │ → session-start hook → generate-commands   │
│  └─────────────────┘                                             │
│                                                                   │
│  方式二：手动执行（立即生效）                                     │
│  ┌─────────────────────────────────────┐                          │
│  │ ./.flow-kit/scripts/generate-commands.sh --force              │ → .claude/commands/ │
│  └─────────────────────────────────────┘                          │
│                                                                   │
│  ⚠️ 注意：不要在 Claude Code 对话框中输入 /flow-kit:register-commands   │
│     来注册命令 —— 因为命令本身需要先注册才能识别，这是先有鸡还是     │
│     先有蛋的问题。正确方式是方式一或方式二。                       │
│                                                                   │
└──────────────────────────────────────────────────────────────────┘
```

### 2.3 调用方式详解

flow-kit 支持四种调用方式，从"推荐"到"备用"依次介绍。

#### 调用方式一：斜杠命令（**推荐**）

在 Claude Code 对话框中直接输入：

```
/flow-kit:health              # 运行健康扫描
/flow-kit:dev-minimal         # 启用极简模式
/flow-kit:ops-guard           # 启用护栏
/flow-kit:phase-1             # 开始需求澄清阶段
```

**优点**：无需记忆路径，AI 助手直接理解意图

#### 调用方式二：@ 引用文件（**启动流程**）

使用 `@` 引用 flow-kit 中的文件：

```
@flow-kit/GO.md                              # 启动完整开发流程
@flow-kit/phases/4-dev/4-dev.md              # 开始开发阶段
@flow-kit/skills/task-master.md              # 调用任务拆解技能
```

**适用场景**：启动一个阶段或调用一个技能

### 3.2 棕地护栏 B1-B6

| 护栏 | 名称         | 检查内容                     | 触发条件       |
| ---- | ------------ | ---------------------------- | -------------- |
| B1   | 文件变更限制 | 单文件修改行数               | > 50 行警告    |
| B2   | 破坏性变更   | API 签名变更、删除公共接口   | 任何破坏性变更 |

| B6   | 测试覆盖率   | 新增代码测试覆盖率           | < 60% 阻断     |

### 3.2.1 棕地项目与绿地项目详解

flow-kit 区分两种项目类型：**棕地项目（Brownfield）** 和 **绿地项目（Greenfield）**。不同项目类型需要不同的工作流程和护栏配置。

---

#### 什么是棕地项目（Brownfield）？

**棕地项目**是指已有代码库的业务迭代开发。例如：

- 正在运营的电商系统、政府企业内部系统
- 已经发布过的移动应用
- 有历史包袱的传统系统现代化改造

**棕地项目的特征**：

| 特征       | 说明                       |
| ---------- | -------------------------- |
| 已有代码库 | 有稳定的功能模块和历史代码 |
| 测试历史   | 有测试记录和 bug 修复历史  |
| 代码不一致 | 代码风格可能不统一         |
| 技术债务   | 可能存在历史遗留问题       |
| 团队熟悉   | 团队成员熟悉现有代码       |

**类比**：就像在已有建筑上装修，需要小心不破坏结构。

---

#### 什么是绿地项目（Greenfield）？

**绿地项目**是指从零开始的新项目开发。例如：

- 全新产品，全新技术栈
- 创业项目的 MVP 开发
- 研究性质的概念验证

**绿地项目的特征**：

| 特征         | 说明                   |
| ------------ | ---------------------- |
| 无历史包袱   | 空白目录，可以自由设计 |
| 代码统一     | 可以统一规划代码风格   |
| 技术选择自由 | 可以选择最新技术栈     |
| 从架构开始   | 需要从零设计架构       |
| 测试体系     | 可以建立完善的测试体系 |

**类比**：就像在一块空地上建新楼，没有约束，可以从一开始就打好基础。

---

#### 棕地项目 vs 绿地项目 核心区别

| 维度               | 棕地项目                 | 绿地项目                 |
| ------------------ | ------------------------ | ------------------------ |
| **起点**           | 已有代码库               | 空白目录                 |
| **护栏**           | 必须全部启用（B1-B6）    | 可适度放宽               |
| **架构**           | 扩展现有架构             | 从零设计                 |
| **测试**           | 补充回归测试             | 建立测试体系             |
| **主要风险**       | 破坏现有功能             | 技术选型风险             |
| **团队要求**       | 熟悉现有代码             | 架构能力要求高           |
| **Phase 2 重点**   | 分析现有架构，找到扩展点 | 设计全新架构，选择技术栈 |
| **护栏 B1**        | 严格限制（> 50 行警告）  | 可放宽                   |
| **护栏 B3**        | 必须（已有数据库）       | 可省略（初期无数据）     |
| **测试覆盖率要求** | ≥ 80%                    | ≥ 60% 即可               |

---

#### 如何判断我的项目是棕地还是绿地？

运行项目类型检测命令：

```bash
$ /flow-kit:project-type detect

[原因] 存在 3 年以上的版本历史，代码量 > 50,000 行

```

**或者手动设置项目类型**：


## 第五章：阶段详解

### 5.1 Phase 0: 变更立项

**目标**: 创建变更标识，评估影响范围

**输入**: 变更描述
**输出**: `CHANGE.md`、change-id

**步骤**:

1. 运行 `/flow-kit:phase:0`
2. 填写变更摘要
3. 评估影响范围（文件数、模块数）
4. 生成唯一 change-id
5. 创建 `.specs/{change-id}/CHANGE.md`

**关键检查点**:

- [ ] change-id 唯一性
- [ ] 影响范围评估完整
- [ ] 变更分类正确（bugfix/feature/refactor）

### 5.2 Phase 1: 需求澄清

**目标**: 明确需求边界和验收标准

**输入**: CHANGE.md
**输出**: `REQUIREMENT.md`

**步骤**:

1. 运行 `/flow-kit:phase:1`
2. 使用 requirement-clarify 技能
3. 定义用户故事和验收标准
4. 识别边界条件和异常场景
5. 创建 `.specs/{change-id}/REQUIREMENT.md`

**关键检查点**:

- [ ] 需求描述清晰无歧义
- [ ] 验收标准可测试
- [ ] 边界条件已识别
- [ ] 依赖项已列出

### 5.3 Phase 2: 架构设计

**目标**: 设计技术方案，选择技术栈

**输入**: REQUIREMENT.md
**输出**: `DESIGN.md`

**步骤**:

1. 运行 `/flow-kit:phase:2`
2. 列出候选技术方案
3. 对比优缺点
4. 选择最优方案并说明理由
5. 创建 `.specs/{change-id}/DESIGN.md`

**关键检查点**:

- [ ] 技术方案对比完整
- [ ] 选型理由充分
- [ ] 风险评估到位
- [ ] 回滚方案可行

**注意**: REFERENCE 文件采用渐进披露，首轮加载 ≤ 150 行

### 5.4 Phase 3: 任务拆解

**目标**: 将设计拆解为可执行任务

**输入**: DESIGN.md
**输出**: `TASK.md`

**步骤**:

1. 运行 `/flow-kit:phase:3`
2. 使用 task-master 技能
3. 拆解为原子任务（每个 < 2 小时）
4. 识别任务依赖关系
5. 检测可并行执行的任务
6. 创建 `.specs/{change-id}/TASK.md`

**关键检查点**:

- [ ] 任务粒度合理
- [ ] 依赖关系清晰
- [ ] 并行机会已识别
- [ ] 风险任务已标记

### 5.5 Phase 4: 开发执行

**目标**: 按任务列表执行开发

**输入**: TASK.md
**输出**: 代码实现、单元测试

**步骤**:

1. 运行 `/flow-kit:phase:4`
2. 按依赖顺序执行任务
3. 遵循 TDD 标准（先写测试，再写实现）
4. 每完成一个任务更新 PROGRESS.md
5. 触发 output-self-check 自检

## 第七章：多代理编排

### 7.1 并行执行引擎

flow-kit v1.12.7 实现了真正的并行执行引擎：

**工作原理**:

1. 使用 bash 后台进程（`&`）启动子代理
2. 使用 `wait` 命令等待所有后台进程完成
3. 记录 PID 支持超时终止和进程管理
4. 原子写入结果文件避免竞态条件

**执行流程**:

```
主代理
  ├── 生成并行计划
  ├── 启动子代理 A (后台) ──→ 执行任务 ──→ 写入结果
  ├── 启动子代理 B (后台) ──→ 执行任务 ──→ 写入结果
  ├── 启动子代理 C (后台) ──→ 执行任务 ──→ 写入结果
  └── wait 等待所有完成 ──→ 聚合结果 ──→ 验证输出
```

### 7.2 子代理重试机制

**配置参数**:

- `max_retries`: 最大重试次数（默认 2 次）
- `retry_interval`: 重试间隔（默认 10 秒）

**重试策略**:

1. 子代理执行失败时自动重试
2. 每次重试记录尝试次数
3. 结果 JSON 包含 `attempts` 字段
4. 超过最大重试次数后标记为 FAILED

**示例输出**:

```json
{
  "id": "agent-1",
  "role": "Code Executor",
  "status": "SUCCESS",
  "attempts": 2,
  "summary": "执行完成（重试 1 次）"
}
```

### 7.3 超时终止机制

**配置参数**:

- `timeout_seconds`: 超时时间（默认 300 秒）
- `check_interval`: 检查间隔（默认 5 秒）

**超时控制**:

1. 每 5 秒检查一次子代理状态
2. 超时自动发送 TERM 信号终止进程
3. 超时结果自动写入 JSON 文件
4. 显示实时进度（完成数/运行中/已用时）

**超时处理流程**:

```
检测超时 → 发送 TERM 信号 → 等待 1 秒 → 发送 KILL 信号 → 写入超时结果
```

### 7.4 结果聚合与验证

**聚合命令**:

```bash
dispatch.sh --aggregate
```

**聚合输出**:

```json
{
  "task_id": "TASK-001",
  "task_desc": "实现用户认证模块",
  "parallel_n": 3,
  "status": "COMPLETED",
  "agents": [
    { "id": "agent-1", "status": "SUCCESS" },
    { "id": "agent-2", "status": "SUCCESS" },
    { "id": "agent-3", "status": "FAILED" }
  ],
  "summary": "2/3 子代理执行成功"
}
```

**验证步骤**:

1. 检查所有子代理状态
2. 验证结果文件完整性
3. 对照目标验证输出
4. 生成最终报告

### 8.4 渐进披露原则

**核心原则**: 按需加载，避免一次性加载过多文件

**文件分类**:
| 类型 | 路径示例 | 典型长度 | 加载方式 |
|------|---------|---------|---------|
| SPEC（项目产物） | `.specs/{change-id}/*.md` | < 200 行 | 整读 OK |
| REFERENCE（查阅型） | `flow-kit/reference/*.md` | 75~470 行 | 禁止默认整读，只 grep/read offset |
| PROMPT/TEMPLATE | `flow-kit/phases/*.md` | < 150 行 | 整读 OK |

**首轮加载约束**: 进入任何阶段时，首轮加载的 REFERENCE 总行数 ≤ 150 行

## 第九章：故障排查

### 9.1 常见问题

**Q1: 上下文窗口溢出怎么办？**

A: 运行上下文压缩：

```bash
context-budget.sh --compress "manual"
```

或使用 caveman-compress 技能进行标准/极限压缩。

**Q2: 子代理执行失败如何处理？**

A: flow-kit 自动重试机制会处理：

- 默认重试 2 次，间隔 10 秒
- 查看日志：`cat .flow-kit/tmp/subagent-{id}.log`
- 手动重试：`dispatch.sh --execute --retry`

**Q3: 如何查看执行进度？**

A: 使用状态命令：

```bash
dispatch.sh --status
```

**Q4: Hooks 未安装如何修复？**

A: 运行安装命令：

```bash
/flow-kit:hooks install
```

**Q5: 项目类型检测不准确？**

A: 手动设置项目类型：

```bash
/flow-kit:project-type brownfield  # 设为棕地
/flow-kit:project-type greenfield  # 设为绿地
```

### 9.2 错误代码参考

| 错误代码 | 描述                 | 解决方案                                |
| -------- | -------------------- | --------------------------------------- |
| E001     | 上下文窗口溢出       | 运行压缩或归档旧变更                    |
| E002     | 子代理执行超时       | 检查任务复杂度，增加超时时间            |
| E003     | 文件锁冲突           | 等待锁释放或手动清理 `.flow-kit/locks/` |
| E004     | JSON Schema 验证失败 | 检查产物格式，参考对应 schema           |
| E005     | 测试覆盖率不达标     | 补充单元测试，确保覆盖率 ≥ 80%          |
| E006     | 破坏性变更检测       | 评估影响，制定迁移方案                  |
| E007     | 安全风险检测         | 修复安全漏洞，重新扫描                  |
| E008     | 性能退化检测         | 优化代码，消除 O(n²) 循环               |

### 9.3 日志分析

**日志位置**:

- 子代理日志：`.flow-kit/tmp/subagent-{id}.log`
- Hooks 日志：`.flow-kit/hooks-log/`
- 执行摘要：`.flow-kit/tmp/dispatch-summary.json`

**查看最近 20 条 Hooks 执行记录**:

```bash
flow-kit.sh hooks summary
```

**分析子代理执行结果**:

```bash
dispatch.sh --aggregate
```

### 9.4 恢复策略

**上下文过期恢复**:

1. 归档旧变更：`/flow-kit:archive`
2. 清理过期文件：`rm -rf .planning/phases/`
3. 重新启动流程

**执行中断恢复**:

1. 查看进度文件：`cat .specs/{change-id}/PROGRESS.md`
2. 使用进度恢复模板：`@flow-kit/skills/subagent-execution.md`
3. 从中断点继续执行

**锁冲突恢复**:

1. 检查锁状态：`ls -la .flow-kit/locks/`
2. 清理过期锁：`rm -rf .flow-kit/locks/{filepath_hash}.lock`
3. 重新执行操作

### D. 文件作用速查表

本节帮助新手快速了解 flow-kit 项目中的文件和目录作用。

#### D.1 你需要操作的目录

| 目录/文件                   | 作用                                     | 新手是否需要操作 |
| --------------------------- | ---------------------------------------- | :--------------: |
| `.planning/PROJECT.md`      | 项目上下文（项目名称、技术栈、团队成员） |   ✅ 需要填写    |
| `.planning/REQUIREMENTS.md` | 需求清单（功能列表、优先级）             |   ✅ 需要填写    |
| `.planning/ARCHITECTURE.md` | 架构设计（技术方案、模块划分）           |   ✅ 需要填写    |
| `.planning/ROADMAP.md`      | 阶段路线图（当前进度、下一步）           |   ✅ 需要更新    |
| `.planning/STATE.md`        | 当前状态（阻塞问题、决策记录）           |   ✅ 需要更新    |
| `.specs/{change-id}/`       | 单次变更的详细规格（每个变更一个目录）   |   ✅ 需要创建    |

#### D.2 不要动的目录

| 目录/文件               | 作用                         | 原因                      |
| ----------------------- | ---------------------------- | ------------------------- |
| `.flow-kit/`            | flow-kit 核心文件目录        | ❌ 禁止修改，升级会覆盖   |
| `.claude/commands/`     | Claude Code 斜杠命令注册目录 | ❌ 禁止手动修改，自动生成 |
| `.flow-kit/phases/`     | 8 阶段流程定义文件           | ❌ 禁止修改，升级会覆盖   |
| `.flow-kit/skills/`     | 元技能包定义                 | ❌ 禁止修改，升级会覆盖   |
| `.flow-kit/guardrails/` | 棕地护栏规则                 | ❌ 禁止修改，升级会覆盖   |

#### D.3 变更规格目录 `.specs/{change-id}/` 内容

每次变更创建一个独立的规格目录，包含以下文件：

| 文件             | 必须？ | 作用                                      |
| ---------------- | :----: | ----------------------------------------- |
| `CHANGE.md`      |   ✅   | 变更摘要（change-id、影响范围、风险评估） |
| `REQUIREMENT.md` |   ✅   | 需求详细说明（用户故事、验收标准）        |
| `DESIGN.md`      |   ✅   | 架构设计（技术方案、决策记录）            |
| `TASK.md`        |   ✅   | 任务列表（原子任务、依赖关系）            |
| `PROGRESS.md`    |   🔄   | 进度记录（完成状态、遇到的问题）          |
| `REVIEW.md`      |   🔄   | 审查报告（三轮审查结果）                  |
| `SUMMARY.md`     |   🔄   | 完成总结（经验教训、后续计划）            |

> ✅ = 必须创建 | 🔄 = 阶段结束时创建

#### D.4 新手操作清单

**首次使用 flow-kit**：

```bash
# 1. 创建项目规划目录
mkdir -p .planning

# 2. 创建第一个变更规格目录
mkdir -p .specs/$(date +%Y%m%d%H%M%S)

# 3. 填写项目上下文
vim .planning/PROJECT.md

# 4. 运行健康扫描确认正常
/flow-kit:health
```

**每次新变更**：

```bash
# 1. 创建变更规格目录
mkdir -p .specs/$(date +%Y%m%d%H%M%S)

# 2. 启动变更立项
@flow-kit/phases/0-change/0-change.md

# 3. 按顺序执行各阶段
@flow-kit/phases/1-requirement/1-requirement.md  # 需求澄清
@flow-kit/phases/2-design/2-design.md           # 架构设计
# ... 以此类推
```

### E. 新手常见错误与解决方案

本节列出新手在使用 flow-kit 时最容易犯的错误，以及如何避免和解决。

#### E.1 上下文过期未感知

**现象**：
Claude Code 开始"遗忘"之前讨论的内容，重复问同样的问题。

**原因**：
上下文窗口使用率超过 80%，开始强制压缩。

**解决**：

```bash
# 1. 检查上下文使用率
/flow-kit:dev-estimate-tokens

# 2. 如果超过 80%，触发压缩
/flow-kit:skill-caveman-compress

# 3. 或者归档旧变更释放空间
/flow-kit:dev-archive
```

**预防**：
每完成一个阶段，运行 `/flow-kit:dev-estimate-tokens` 检查上下文使用率。

---

#### E.2 跳过 Phase 直接写代码

**现象**：
代码写完后发现需求理解错误，需要大量返工。

**原因**：
没有按顺序执行 Phase 0-2，直接进入 Phase 4 开发。

**解决**：

```bash
# 1. 确认当前阶段
# 查看 STATE.md 确认当前进度

# 2. 如果在 Phase 1（需求澄清）之前，需要补做
@flow-kit/phases/1-requirement/1-requirement.md

# 3. 如果在 Phase 2（架构设计）之前，需要补做
@flow-kit/phases/2-design/2-design.md
```

**预防**：
严格按顺序执行 Phase，phase-0 → phase-1 → phase-2 → ... → phase-7。

---

#### E.3 多代理执行后忘记聚合

**现象**：
子代理结果分散在各个临时文件，看不到完整输出。

**原因**：
执行 `dispatch.sh --execute` 后没有运行聚合命令。

**解决**：

```bash
# 1. 查看执行状态
dispatch.sh --status

# 2. 聚合所有子代理结果
dispatch.sh --aggregate

# 3. 查看聚合结果
cat .flow-kit/tmp/dispatch-summary.json
```

**预防**：
执行 `--execute` 后必须运行 `--aggregate`，这是固定的工作流程。

---

#### E.4 多个变更规格混在一起

**现象**：
`.specs/` 目录下有多个变更混在一起，不知道哪个是哪个。

**原因**：
没有为每个变更创建独立的规格目录。

**解决**：

```bash
# 为每个变更创建独立的目录
mkdir -p .specs/$(date +%Y%m%d%H%M%S)

# 例如
mkdir -p .specs/20260511120000  # 变更 A
mkdir -p .specs/20260511143000  # 变更 B

# 在各自目录下工作
cd .specs/20260511120000
```

**预防**：
一个变更 = 一个独立目录，目录名使用时间戳确保唯一性。

---

#### E.5 护栏阻断后不知道如何处理

**现象**：
提交代码时 B1-B6 护栏阻断，不知道如何解决。

**原因**：
护栏检测到风险（破坏性变更、安全问题、性能问题等）。

**解决**：

```bash
# 1. 查看护栏阻断原因
/flow-kit:ops-careful

# 2. 根据阻断原因处理：
# - B1 (文件变更过大): 拆分任务，减少单文件修改行数
# - B2 (破坏性变更): 评估影响，确保向后兼容或标注 breaking change
# - B3 (数据库风险): 制定回滚方案
# - B4 (安全问题): 修复安全漏洞（凭据泄露、注入等）
# - B5 (性能问题): 优化代码（消除 O(n²) 循环等）
# - B6 (测试覆盖率不足): 补充单元测试

# 3. 修复后重新检查
/flow-kit:ops-careful
```

**预防**：
开发过程中定期运行 `/flow-kit:ops-careful`，早发现早修复。

---

#### E.6 项目类型设置错误

**现象**：
棕地项目没有启用护栏，或者绿地项目被错误限制。

**原因**：
没有手动设置或自动检测项目类型。

**解决**：

```bash
# 1. 检查当前项目类型
/flow-kit:health

# 2. 如果错误，手动设置
/flow-kit:project-type brownfield  # 棕地项目
/flow-kit:project-type greenfield  # 绿地项目

# 3. 棕地项目确保启用护栏
/flow-kit:ops-guard full
```

**预防**：
首次使用 flow-kit 时运行健康扫描，确认项目类型正确。
