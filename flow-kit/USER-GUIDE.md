## 第一章：概述

### 什么是 flow-kit

flow-kit 是面向 Claude Code 的结构化开发流程工具包，提供 8 阶段开发工作流、护栏规则和状态追踪。

### 核心特性

| 特性          | 说明                               |
| ------------- | ---------------------------------- |
| 8 阶段工作流  | 从需求立项到集成归档               |
| 状态追踪      | `.flow-kit/current-phase` 追踪进度 |
| 棕地/绿地分叉 | 不同项目类型走不同工作流           |
| 护栏 B1-B6    | 保护代码库免受破坏性变更           |

### 术语表

| 术语       | 定义                           |
| ---------- | ------------------------------ |
| Phase      | 开发流程阶段，共 0-8 九个阶段  |
| Brownfield | 棕地项目，已有代码库的迭代开发 |
| Greenfield | 绿地项目，从零开始的新项目     |
| Change ID  | 变更唯一标识符                 |
| Guardrail  | 护栏规则，安全检查             |

## 第二章：快速开始

### 首次使用

```bash
# 1. 创建变更规格
./flow-kit.sh change init "添加用户反馈中心"

# 2. 查看当前状态
./flow-kit.sh status

# 3. 启动 Phase 0
/flow-kit:phase-0

# 4. 推进到下一阶段
/flow-kit:next
```

## 第三章：核心概念

### 8 阶段工作流

```
Phase 0 ── Phase 1 ── Phase 2 ── Phase 3
  │         │         │         │
  ▼         ▼         ▼         ▼
变更立项  需求澄清  架构设计  任务拆解

Phase 4 ── Phase 5 ── Phase 6 ── Phase 7
  │         │         │         │
  ▼         ▼         ▼         ▼
开发执行  测试验证  代码审查  集成归档
                │
                ▼
           Phase 8 (变更回滚)
```

### 状态追踪

flow-kit 通过 `.flow-kit/current-phase` 文件追踪当前阶段：

```bash
# 查看当前阶段
cat .flow-kit/current-phase

# 输出示例：1
```

### 护栏 B1-B6

| 护栏 | 说明           | 棕地 | 绿地 |
| ---- | -------------- | :--: | :--: |
| B1   | 文件变更限制   |  ✅  |  -   |
| B2   | 破坏性变更检测 |  ✅  |  ✅  |
| B3   | 数据库安全     |  ✅  |  -   |
| B4   | 安全检查       |  ✅  |  ✅  |
| B5   | 性能护栏       |  ✅  |  -   |
| B6   | 测试覆盖率     | ≥80% | ≥60% |

### 棕地 vs 绿地

**棕地项目**（已有代码库）：

- 必须启用全部护栏 B1-B6
- 重点：保护现有功能不破坏
- 架构：分析现有架构，找扩展点

**绿地项目**（新项目）：

- 可用核心护栏（B2/B4/B6）
- 重点：建立开发规范
- 架构：从零设计全新架构

## 第五章：阶段详解

### Phase 0: 变更立项

**目标**: 创建 change-id，评估影响范围

**步骤**:

1. 运行 `/flow-kit:phase-0`
2. 评估影响范围
3. 生成 change-id
4. 创建 `.specs/{change-id}/CHANGE.md`

**棕地项目重点**: 影响范围评估、破坏性变更识别
**绿地项目重点**: 项目愿景、技术选型

---

### Phase 1: 需求澄清

**目标**: 明确需求边界和验收标准

**步骤**:

1. 运行 `/flow-kit:phase-1`
2. 定义用户故事
3. 制定验收标准
4. 识别边界条件

**棕地项目重点**: 理解现有代码、回归测试计划
**绿地项目重点**: MVP 定义、非功能需求

---

### Phase 2: 架构设计

**目标**: 设计技术方案

**步骤**:

1. 运行 `/flow-kit:phase-2`
2. 列出候选方案
3. 对比优缺点
4. 设计架构

**棕地项目重点**: 分析现有架构、找扩展点、回滚方案
**绿地项目重点**: 全新架构设计、技术选型

---

### Phase 3: 任务拆解

**目标**: 拆解为可执行任务

**步骤**:

1. 运行 `/flow-kit:phase-3`
2. 拆解为原子任务（< 2 小时）
3. 识别依赖关系
4. 标记可并行任务

---

### Phase 4: 开发执行

**目标**: 按任务列表执行开发

**步骤**:

1. 运行 `/flow-kit:phase-4`
2. TDD 开发（先写测试）
3. 每次提交前运行护栏检查
4. 更新 PROGRESS.md

---

### Phase 5: 测试验证

**目标**: 验证代码质量和功能正确性

**步骤**:

1. 运行 `/flow-kit:phase-5`
2. 运行所有测试
3. 检查覆盖率

**棕地要求**: 新增覆盖率 ≥ 80%
**绿地要求**: 新增覆盖率 ≥ 60%

---

### Phase 6: 代码审查

**目标**: 三轮审查确保代码质量

**步骤**:

1. 第一轮：架构审查
2. 第二轮：设计审查
3. 第三轮：工程审查

---

### Phase 7: 集成归档

**目标**: 合并代码，沉淀经验

**步骤**:

1. 合并代码到主分支
2. 更新文档
3. 归档变更规格
4. 提取经验教训

---

### Phase 8: 变更回滚

**目标**: 紧急回滚变更

**触发**: 生产环境出现严重问题

## 第六章：棕地 vs 绿地

### 核心差异

| 维度             | 棕地 (brownfield)      | 绿地 (greenfield)   |
| ---------------- | ---------------------- | ------------------- |
| **护栏**         | B1-B6 全开             | 核心护栏 (B2/B4/B6) |
| **测试覆盖**     | ≥ 80%                  | ≥ 60%               |
| **Phase 2 重点** | 分析现有架构，找扩展点 | 设计全新架构        |
| **回滚方案**     | 增量回滚               | 整体重建            |
| **风险**         | 破坏现有功能           | 技术选型风险        |

### 项目类型检测

```bash
# 自动检测（基于锁文件、git history、代码行数）
# Phase 0 自动执行，无需手动命令

# 手动设置（写入 .flow-kit/project-type）
echo "project_type: brownfield" > .flow-kit/project-type
echo "project_type: greenfield" > .flow-kit/project-type
```

### 工作流文件结构

```
phases/
├── 0-change/
│   ├── 0-change.md      # 通用触发条件
│   ├── brownfield.md    # 棕地专用
│   └── greenfield.md    # 绿地专用
├── 1-requirement/
│   └── ...
```

条件路由由 `scripts/phase-executor.sh` 实现。
