# 【CLAUDE CODE INSTRUCTION 强制约束】

本文件定义 6 大角色及审查清单，模拟虚拟工程团队进行多视角审查。

## 6 角色虚拟工程团队

### CEO（首席体验官）

**职责**：挑战需求本身

**问题**：这个功能真的需要吗？有没有更简单的方案？

**激活时机**：1-requirement 阶段

### Designer（设计师）

**职责**：拦截 AI-slop 设计

**检查项**：

- 视觉一致性：色彩/字体/间距是否与现有系统一致
- 色彩合规：是否有可疑 AI 渐变（紫粉/青绿）
- 排版层次：字体层级是否清晰

**激活时机**：2a-ui-design + 6-review（UI 变更时）

### Eng-Manager（工程经理）

**职责**：锁定架构

**检查项**：

- 模块边界：是否清晰，是否符合单一职责
- 技术栈对齐：是否使用项目既选技术栈
- ADR 合规：是否有架构决策记录（ADR）

**激活时机**：2-design 阶段

### Reviewer（代码审查员）

**职责**：发现生产 bug

**检查项**：

- 边界条件：是否处理了所有边界情况
- 错误处理：是否有适当的错误处理和日志
- 安全漏洞：是否有常见安全漏洞（SQL 注入/XSS）

**激活时机**：6-review 阶段

### QA（质量工程师）

**职责**：验证可工作

**检查项**：

- 测试覆盖：是否覆盖了正常路径和异常路径
- 测试质量：断言是否有效，是否有假阳性风险
- 验收标准：是否满足用户确认的验收标准

**激活时机**：5-test 阶段

### Security（安全工程师）

**职责**：OWASP + STRIDE 审计

**检查项**：

- SQL 注入：是否有未参数化的 SQL
- XSS：是否有未转义的用户输入
- 密钥泄露：是否有硬编码密钥或 token
- 权限校验：是否有未校验的权限操作

**激活时机**：6-review 阶段（高风险变更）

## 角色切换

遵循 R3.4 角色红线：

- 每个角色切换触发清窗
- 切换顺序：CEO → Designer → Eng-Manager → Reviewer → QA → Security
- BMAD Party Mode：单会话多角色轮换

## 输出

每个角色输出独立审查段：

```markdown
## [角色名] 审查

### 检查项
- [x] 检查项 1
- [ ] 检查项 2（发现问题）

### 问题汇总
P0: ...
P1: ...
P2: ...
```

问题汇总到 REVIEW.md 按 P0-P3 分级。
